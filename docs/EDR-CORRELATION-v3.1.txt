AsterTrack 跨进程关联与采集策略 定稿（v3.1）
=================================================
日期：2026-10-08
定位：商业级分布式 EDR 核心引擎架构
=================================================


【一、核心哲学】
1. 骨架与血肉分离：exec 维护血缘表骨架，file/tcp 提供异常节点血肉。
2. 内存做关联，磁盘做兜底：高频事件在内存消化，磁盘仅用于断网缓存与状态快照。
3. 宁可少采，绝不打垮宿主：内核态有限流，本地落地有硬配额。


【二、血缘表机制】
1. Key: (pid, start_time_ns)（复合键，防 PID 重用）
2. Value: { ppid, ppid_start_time_ns, corr_key, is_anchor, created_at, last_seen }
3. 存储: sync.Map 或 Actor 管理
4. 容量上限 50000 条（建议 2000），超限 LRU 淘汰


【三、锚点生成规则】
1. exec 事件：不创建新锚点，继承父进程 corr_key。
2. 孤儿进程（父为 init/systemd）：独立生成新锚点。
3. file_access/bash/tcp 事件：若无 corr_key，则创建新锚点。
4. 多级上溯：exec 寻找锚点时，最多上溯 5 层。
5. 暂不做 namespace_id。


【四、采集策略】
exec: 全采 + 剔除系统进程
bash: 全采 + 剔除空/重复
file_access: 默认不采 + 敏感路径
tcp: 计数 + 星轨激活转明细
xdp: 保底通道，默认不启用，仅 Agent 掉线时激活
     - Token Bucket 限流
     - ENABLE_XDP 编译/配置开关


【五、强制观测清单（不可关闭）】
1. 进程生命周期（exec 全采）
2. 关键系统文件（/etc/shadow、/etc/passwd、/etc/crontab、/root/.ssh/）
3. 公网外联（非内网 IP，至少计数）
4. CMDB 资产变更
5. Agent 自身健康
底层通过位掩码硬约束。
例外：super-admin + 二次确认可临时调整。


【六、规则分层设计】
L1 原子规则（C/Go 层）：单探针单事件匹配。
L2 序列规则（Go 层）：同 corr_key 下的事件序列匹配，触发星轨。
  - 先做"简单 AND"
  - L2 视为"小编排引擎"，未来无缝迁移到大编排引擎
L3 树形规则（Server 层）：跨进程树、跨主机。


【七、规则冲突仲裁】
1. 强制观测 > 用户规则 > 系统默认
2. 单机规则只能收紧，不能做减法
3. 同层冲突：安全优先（采 > 不采），高权限用户优先
4. 必须实现冲突检测器


【八、本地持久化（LBE 模块）】
1. 形式：环形 Append-Only 文件 + meta.json
2. 默认配额：200MB（16MB × 12 段 或 32MB × 6 段）
   - UI 滑块可调：100MB - 1GB（无上限，用户自负）
3. 写入：内存 Channel（10000 容量）+ 批量刷盘（1000条或1秒）
4. 三不存 / 三必存：
   - 三不存：普通 file_access 流水、内网 tcp 明细、高频重复命令
   - 三必存：血缘状态与锚点快照、L2命中告警及星轨明细、断网期间待上报事件
5. 极致压缩（断网时可 CPU 换空间）：
   - 通用：Snappy
   - exec/bash：只存核心字段（pid, ppid, start_time, comm, argv_hash）
6. 完整性机制（不做 HMAC）：
   - 每条记录：CRC32
   - 段头：CRC32
   - 关键数据：复用 Server 下发时的原签名
   - 普通事件：无签名，靠 Server 侧交叉验证
   - 不做 HMAC：内存密钥重启即丢，落盘则失去意义
7. 磁盘 Guardian：
   - 每 10 秒检查磁盘剩余空间
   - 默认阈值：软/硬 各 1GB（用户可调）
   - 触发动作：清空 LBE 一半 + 降级"仅内存队列" + 熔断 + 告警
   - 熔断后不再尝试落盘
   - 降级期间可用 CPU 换空间
8. 断网重传：
   - 网络恢复后从最旧段重传
   - 限速 1MB/s 或 1000条/s
   - Server 基于 corr_key + timestamp 幂等去重


【九、跨主机关联（Server 端）】
1. Agent 只管单机血缘，Server 负责跨主机
2. 匹配 tcp 五元组（A的 dstIP == B的 srcIP && A的 dstPort == B的 srcPort）
3. P1 阶段：只做基本 IP+Port 匹配
4. NAT 优化留 P1


【十、动作层设计】
拦截动作全部交给 LSM（内核态），Agent 不做 kill/block。

编排引擎（未来）触发动作：
  ├─ 对 LSM：下发拦截规则
  ├─ 对 AF（外部防火墙）：下发策略
  ├─ 对探针：切模式
  ├─ 对 Agent：上报节奏调整
  └─ 对告警：升级 / 抑制 / 合并

C1 安全事件审计：
  - 记录"为什么认为这是攻击"（判定依据 + 事件证据）
  - 例 1：软基线异常（DoS 突增 → 记录偏离统计）
  - 例 2：硬规则命中（"/dev/tcp/xxx" → "cat /etc/passwd" 序列）

C2 编排引擎指挥 AF：预留（等 AF 接入时具体化）


【十一、落地阶段】

阶段 0：清基础（1-2 天）
阶段 1：血缘表 + 锚点（3-5 天）
阶段 2：L2 规则引擎（3-5 天）
阶段 3：LBE + Guardian（1-2 周）
阶段 4：跨主机关联（3-5 天）
阶段 5：强制观测位掩码（1-2 天）


【十二、预期效果】

做完阶段 0-2（"打通上下文关联"）：
  - 血缘表正确工作
  - 5 探针 corr_key 统一
  - L2 序列规则生效
  - 前端能看到完整攻击链

完成所有阶段：
  - 事件自动串成攻击链
  - 跨主机关联
  - 断网不丢关键证据
  - 编排引擎 + LSM 后：实时拦截

结构性阻碍：清
精度问题：后续调参
永久阻碍：加密内容 / 文件内容 / 攻击者反制


【十三、远期（P2）】
Client 数据加解密：
  - 目标：LBE + 上报数据全加密
  - 密钥源：TPM / machine-id 派生（KDF）
  - 算法：AES-GCM
  - 工作量：1-2 周
