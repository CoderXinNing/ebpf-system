编排引擎（行为引擎）设计备忘
=================================================
状态：设计阶段，未开工
创建：2026-09-24
用途：新会话接着做时的上下文交接
=================================================


【目标】
按进程画像决定探针组合，而非"全机全探针"。

核心洞察：不同类型进程的"攻击行为"不同。
- 中间件（Nginx/PHP/Tomcat）→ 敏感文件 + 系统调用 + 命令执行才是信号
- 流量探针对中间件无意义（正常业务流量太大，噪声淹没信号）


【优先级链】从高到低
1. 黑名单  → 必须监控/告警（管理员最强意志）
2. 白名单  → 不告警，事件仍记录（降噪，非失明）
3. 画像    → 按组合上报
4. 默认    → 全探针

"管理员说什么都是对的" = 黑/白名单是绝对意志，画像和默认都不能覆盖。
黑名单 > 白名单。


【关键决策】
- 探针组合冲突 → 并集 + 配置预警（安全优先，不漏报）
- 画像继承     → 深度限制 3 层（覆盖攻击链，防爆炸）
- 白名单 vs 画像 → 白名单优先（事件仍上报，只降噪）
- 学习时机     → 24h 窗口采样，固化（不持续学习）
- 学习范围     → 只学匹配键（comm/exe/unit），不学行为内容
- 学习持久化   → Server DB（跨主机可复用，容灾不需重学）
- 特征变化     → 匹配失败 → 报警 → 人工确认（不自动适应）


【学习机制】
只学匹配键，不学行为内容：

  管理员选 nginx.service
    ↓ 24h 学习窗口
  提取稳定特征：
    ✅ comm = "nginx"（100% 样本一致）→ 主键
    ✅ exe = "/usr/sbin/nginx"（100% 一致）→ 辅助
    ❌ cmdline（master/worker 不一致）→ 不学
    ❌ 读的文件（每天不同）→ 不学
    ↓ 管理员确认
  固化到 DB，之后纯匹配

日志路径带日期不是问题：
- 画像只负责"哪些进程的哪些事件上报"
- 不负责"事件内容的模式匹配"
- /var/log/2020-1-1 和 /var/log/2020-1-2 都上报，不需要学习


【匹配键】
- comm          复用 sentinel_whitelist map，复杂度低
- PID           复用 G2 进程树，复杂度中
- systemd unit  /proc/<pid>/cgroup + 缓存，复杂度高（最复杂）


【作用域与下发】
- 作用域：Agent 级（同机不同实例可不同配置）
- 下发：前端 UI 配置 → Server DB → 下发 Agent → C 层加载
- 生效层：C 层过滤（建议，符合守则第 5 条）


【分三期实施】

期 1：MVP（~1 周）
- 只做 comm 匹配
- 画像 CRUD（数据库表）
- 简单前端 UI（启用/禁用默认名单）
- C 层加载画像 comm 列表，非画像进程丢事件

期 2：扩展匹配维度（~1 周）
- PID 匹配（复用 G2 进程树）
- systemd unit 匹配
- 学习机制（24h 采样 + 固化）
- 自定义画像

期 3：高级编排（~1 周）
- 黑名单
- 3 层继承
- 组合并集 + 冲突预警
- 配置冲突检测


【画像冲突场景（需处理）】
1. 一进程匹配多画像（同维度）→ 并集
2. 一进程匹配多画像（跨维度）→ 并集 + 预警
3. 父子进程跨画像 → 继承（3 层）
4. exec 后画像切断 → 跟随 cgroup（如适用）
5. 默认 vs 自定义 → 自定义优先
6. 宽匹配 vs 窄匹配 → 并集
7. 画像 vs whitelist → whitelist 优先
8. 画像 vs 强制观测底线 → 底线优先（画像选项灰显）
9. 配置时进程不存在 → 按条件存，出现时命中
10. 继承链爆炸 → 深度限制 + pid 数量上限


【不做】
- 学行为内容（日志路径等变动的东西）
- 流量探针加入中间件画像
- 持续学习（成本不高但收益低 + 隐患）
